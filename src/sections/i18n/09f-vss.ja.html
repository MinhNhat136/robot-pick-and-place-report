IV.05 節 · VSS による動画評価

視覚言語モデルに動画を見せ、結果を自動で判定させる。

NVIDIA VSS（Video Search & Summarization）は、視覚言語モデル（VLM）で動画を分析するツール群です。本節では GPU サーバーへの VSS 3.2.1 のインストール手順を示し、Isaac Sim → VSS ブリッジを使ってハンマー → ビンのエピソード動画を VSS に見せ、成功か失敗かを判定させて Arena の判定と比較します。各ステップにはコマンド、期待される結果、実際の操作を録画した動画があります。

3 つの判定方法と 99 エピソードでの結果

ブリッジには VSS の 3 つの仕組みに対応する 3 つのプログラムがあります。それぞれ YAML の設定ファイルを読み、エピソードごとの結果（epNNN.json）と集計表 report.md を書き出します。

判定方法仕組み時間デコード
動画要約（LVS）
vss_bridge.run_pipeline		動画を /v1/summarize（ポート 38111）に送信。VLM が要約とイベントのタイムラインを書き、ブリッジが厳密なルールでイベントから判定を読み取る約 22 秒 / エピソード既定（ランダムサンプリングあり）
Q&A
vss_bridge.qa_agent		エージェント（ポート 8000）が VLM に質問：「動画の終了時、ハンマーは完全にビンの中にあるか？ YES/NO」約 82 秒 / エピソード既定（ランダムサンプリングあり）
リアルタイムアラート（RT alert）
vss_bridge.rt_alert		各エピソードを固定の 8 秒枠に収める。VLM（ポート 8018）が「失敗はあるか？ Yes / No」に回答。Yes = アラート = 失敗ライブストリームの 8 秒区間ごとに約 0.7 秒既定、修正版：top_k: 1

評価には Arena の判定が付いたハンマー → ビンの 99 エピソードを使いました。13 エピソードは質問と結果の読み取り方の調整用、86 エピソードは判定専用に取り分けたものです。比較の基準は常に「成功」と答える方法で、ほとんどのエピソードが成功するため 63/86（73.3 %）正解します。この基準を上回って初めて判定方法として役に立ちます。

固定の 8 秒枠が重要な理由：成功したエピソードは成功条件を満たした時点で止まるため、クリップが短くなります。動画要約と Q&A では、クリップの長さだけで 86 エピソードすべての結果を当てられてしまいます。リアルタイムアラートはすべてのエピソードを同じ長さにそろえるためこの漏れがなく、これがその結果を最も公平な試験とする理由の一つです。

動画要約52/86（60.5 %）56 %74 %いいえ

結果がばらつく原因（確認済み）：同じ設定・同じフレームでも、リアルタイムアラートの実行同士で 86 エピソード中 28 件の判定が食い違いました。1 つのクリップを 8 回送ると「Yes」が 5 回、「No」が 3 回でした。リアルタイム VLM サービスは temperature が 0 でないときだけモデルに渡すため、temperature 0 は捨てられ、モデルは既定の 1.0 でサンプリングします。top_k: 1 を加えると決定的なデコードになり、2 回の実行が 99 エピソードすべてで一致し、Arena との一致率は 94.2 % に上がりました。成功はすべて、失敗は 23 件中 18 件を認識しています。
94.2 % は有力な手がかりであり、まだ確定した結果ではありません。質問は変えていませんが、この実行は取り分けたエピソードの結果を知った後に行いました。調整用の 13 エピソードでは 8/13 しか正解せず、ロボットの転倒 2 件をどちらも見逃しています。取り分けたエピソードには転倒が 1 件もありません。新しいデータでの実行で確認する必要があります。動画要約と Q&A も同じデコードの欠陥の影響を受けており、まだ top_k: 1 で再実行していないため、3 つの方法の比較はまだ公平ではありません。
  • Q&A は成功 63 件中 31 件を「ハンマーは一部だけビンの中」などの回答で失敗と判定しました。2 つのグループの最終フレームと Arena の測定値はほぼ同じです。原因として考えられるのは、ビンの底が浅いことと、質問中の「完全に」（fully）という語です。
  • VSS のエージェントは質問を書き換えてから VLM に渡しており、それが 99 件中 46 件ありました。実際に尋ねた質問は一定ではありませんでした。

発見事項と対応

#発見事項対応担当
1dev-profile.sh --dry-run でも generated.env を上書きし、data-dir の権限を変更するDry-run は一時的な clone でのみ（ステップ 5）スクリプトを実行する人
2docker-ce、docker-ce-cli が現在固定されていない。apt upgrade で Docker が検証済みの範囲外になりうるsudo apt-mark hold docker-ce docker-ce-cli管理者
3VLM サービスが temperature 0 を捨てて 1.0 でサンプリングする：同じ動画でも答えが変わる3 つの方法すべてで top_k: 1 を送る。動画要約と Q&A を top_k: 1 で再実行技術リーダー
494.2 % は取り分けたエピソードの結果を知った後に測定。そのエピソードにはロボットの転倒がない転倒を含む新しいエピソードでの実行で確認技術リーダー
5エージェントが 99 件中 46 件で質問を書き換えた。Q&A は成功 63 件中 31 件を失敗と判定VLM に送る質問を固定し、「完全に」の代わりに「ビンの中」を明確に定義する技術リーダー
6ヘルスチェックが healthy のまま VLM エンジンが 10 月 19 日から停止していた。ディスク満杯で Kafka が止まり、Elasticsearch が読み取り専用になったヘルスチェックだけでなく、実際の VLM 呼び出しとディスク使用量で監視する管理者
結論：現在の設定では、動画要約と Q&A は常に「成功」と答える基準（73.3 %）を上回りません。top_k: 1 のリアルタイムアラートは取り分けた 86 エピソードで 94.2 % に達し、高速（8 秒区間ごとに 1 秒未満）で安定しており、今後追うべき方向です。VSS で Arena の判定を置き換えたり補ったりする前に、新しいエピソードでの確認の実行と、残る 2 つの方法の top_k: 1 での再実行が必要です。

日常の運用

以下は vss/deploy/docker で、E=developer-profiles/dev-profile-lvs/generated.env として実行します。

作業コマンド
ログを見るdocker logs --tail 200 vss-lvs（または vss-rtvi-vlm、vss-agent）
データを残したまま全体を停止 / 起動docker compose --env-file $E stop / start
GPU を空けるdocker stop vss-rtvi-vlm、再開は docker start vss-rtvi-vlm
Docker デーモンの再起動後docker start kafka phoenix（この 2 つは自動で再起動しない）
LLM モデルの変更$E の LLM_NAME を編集し、docker compose --env-file $E up -d --no-deps --force-recreate lvs-server vss-agent
定期確認VLM を実際に呼び出し（カード 4 の表の VLM の行）、df -h / を確認する。ヘルスチェックは VLM の停止を検出できない。ディスク満杯で Kafka が止まり、Elasticsearch が読み取り専用になる（承認を得て古いデータ 79 GB を削除した）
インストール済みのマシンで dev-profile.sh up や down を実行しないでください：17.8 GB のモデルボリュームが削除され、sudo も必要です。generated.env や keys.env を cat したり、grep なしで docker compose config や docker inspect を実行したりもしないでください：キーが画面に表示されます。
